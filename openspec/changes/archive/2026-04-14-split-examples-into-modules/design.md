## Context

The clarity-examples project is today a single Gradle module with 41 sibling directories under `src/main/java/skadistats/clarity/examples/`. Each directory contains a `Main.java` and gets a `<name>Run` + `<name>Package` task generated by a `fileTree(…)` walk in the root `build.gradle.kts`. Users of Clarity visit this project to learn the API; the maintainer uses it to house issue reproducers, diagnostic tools, and benchmarks. These audiences are increasingly poorly served by a flat list because an external user wading in cannot tell which examples teach the API and which are research scaffolding.

This is the first of a planned five-proposal arc. The follow-ups (`add-example-launcher`, `add-replay-runner`, `normalize-run-configs`, `restructure-replays`) all need a stable place to land — specifically, `add-example-launcher` and `add-replay-runner` need a `launcher/` module to drop their code into.

## Goals / Non-Goals

**Goals:**
- Separate the four audiences (teach / reproduce / diagnose / benchmark) into distinct Gradle subprojects visible at the top of the repository.
- Establish `launcher/` as an empty-but-buildable subproject ready to receive launcher + runner code from follow-up proposals.
- Preserve muscle-memory task invocation (`./gradlew <name>Run`) when names remain unique.
- Preserve per-example uno-jar packaging exactly as today.
- Preserve `.java` logic unchanged — this is a move + rename, not a rewrite.

**Non-Goals:**
- Do not introduce the `ExampleLauncher` helper or the `ReplayRunner` entry point (follow-up proposals).
- Do not touch `.idea/runConfigurations/*.xml` beyond what the move breaks — the normalize-run-configs proposal handles those once the launcher exists to point them at.
- Do not change the `replays/` tree.
- Do not change logback configuration, dependencies, or Java version.

## Decisions

### D1. Subprojects, not source sets or packages

**Choice:** five sibling Gradle subprojects (`examples`, `repro`, `dev`, `bench`, `launcher`) sharing one settings file.

**Alternatives:**
- *One module, multiple source sets.* Kept the single-module feel but sacrificed visible separation in the repo root and did nothing for parallel build; source sets also have awkward IDE integration.
- *Package-only split, no Gradle change.* Keeps today's build but buries the category in a Java package name where nobody looks. Doesn't solve the "new contributor can't find things" problem.
- *Full multi-repo.* Overkill — the four audiences share dependencies, release cadence, and maintainer.

**Rationale:** subprojects put the category at the top of the repo tree where it's immediately visible, give each subproject its own `build.gradle.kts` for future per-category customization (e.g. bench might enable JMH plugin later), and let Gradle parallelize builds across subprojects.

### D2. `launcher/` exists but is empty

**Choice:** create `launcher/` as a scaffolded subproject with an empty source tree and a trivial `build.gradle.kts`. No main class, no code.

**Alternative:** defer `launcher/` until `add-example-launcher` runs. Rejected because then `add-example-launcher` carries both "create subproject" and "add helper code" as a single change — too much for one proposal, and the subproject scaffolding concern belongs here alongside the other four.

### D3. Java package names include the category segment

**Choice:** subproject `examples/` keeps today's `skadistats.clarity.examples.<name>` package. The other three add a segment:

```
examples   →  skadistats.clarity.examples.<name>                 (unchanged)
repro      →  skadistats.clarity.examples.repro.<name>
dev        →  skadistats.clarity.examples.dev.<name>
bench      →  skadistats.clarity.examples.bench.<name>
launcher   →  skadistats.clarity.examples.launcher
```

**Alternative:** keep every package as `skadistats.clarity.examples.<name>` regardless of subproject. Rejected because then a reader seeing `import skadistats.clarity.examples.dtinspector.Main;` has no signal whether this is a supported teaching example or a maintainer tool. With the segment included, the category is visible at every import site.

**Trade-off:** this is a one-time package rename touching every moved `.java` file. IDE refactoring handles it mechanically. The alternative would have required zero rewrites but permanently ambiguous imports.

### D4. Shared convention plugin in `buildSrc/`

**Choice:** the per-directory task generation (`allchatRun`, `allchatPackage`) moves out of the root `build.gradle.kts` and into a convention plugin under `buildSrc/src/main/kotlin/`. Each subproject applies it in one line.

**Alternative:** each subproject repeats the task-generation block. Rejected — duplicates logic across five files and guarantees drift.

### D5. Task names stay unqualified when unique

**Choice:** the convention plugin generates tasks with the leaf directory name (`allchatRun`, not `examplesAllchatRun`). Gradle resolves `./gradlew allchatRun` as long as the name is unique globally; if two subprojects ever contain the same directory name (unlikely — we'll steer against collisions in proposal review), callers fall back to `:<subproject>:<name>Run`.

**Alternative:** always qualify task names (`examplesAllchatRun`, etc.). Rejected because it breaks every existing script, README line, and memory of every user who's run these. The break-on-collision fallback costs nothing in practice.

### D6. Convention plugin reaches replays via `rootProject.projectDir`

**Choice:** every subproject resolves the `replays/` symlink as `rootProject.projectDir/replays`. No per-subproject replay symlink.

**Rationale:** one symlink to maintain; subprojects don't care where they sit in the tree.

## Risks / Trade-offs

- **[R1] Muscle memory break: `./gradlew <name>Run` stops working for names that later collide.**
  → Mitigation: initial move chooses subproject placement such that no collisions occur today (checked during tasks); document the qualified form in README so users know the escape hatch exists from day one.

- **[R2] IDE run configs all break on module rename.**
  → Accepted. This was already the case (configs split `clarity-examples` vs `clarity-examples.main`). The follow-up `normalize-run-configs` proposal fixes this properly; this proposal only notes the break.

- **[R3] Package rename touches every moved `.java` file.**
  → Mitigation: IDE refactor tool handles it atomically per file; executed as one commit per subproject during the move phase to keep diff reviewable.

- **[R4] `buildSrc/` adds build-time cost (compilation of the convention plugin on first build).**
  → Accepted — one-off few-seconds cost per clean build. Small compared to the duplication it avoids.

- **[R5] External documentation (blog posts, tutorials) referencing old task names.**
  → Mitigation: leaf task names are preserved; only the *directory path* changes, not the Gradle command. External docs that say `./gradlew allchatRun` keep working.

## Migration Plan

Executed as a single logical change (can be split into commits per subproject, but lands atomically):

1. Create `buildSrc/` with the convention plugin encapsulating today's task generation.
2. Create the five subproject directories with minimal `build.gradle.kts` applying the plugin, and register them in `settings.gradle.kts`.
3. Move each of the 41 current example directories into its new subproject (`git mv`), rewriting `package` declarations for the three categories that gain a segment (repro/dev/bench).
4. Prune the per-example task generation from the root `build.gradle.kts`.
5. Run `./gradlew build` to confirm every subproject compiles and every `<name>Package` task still produces its jar.
6. Update `README.md` and `CLAUDE.md` with the new layout and task-name rules.

No rollback plan needed — the move is a pure reorganization. If something goes wrong, revert the commits.

## Open Questions

- `resources/` is an awkward Java package name (shadows Gradle's `src/main/resources/` convention). Renaming to something descriptive is tempting but not required by this proposal. Decision deferred to tasks; default is to leave it as `resources` unless the move surfaces a concrete problem.
